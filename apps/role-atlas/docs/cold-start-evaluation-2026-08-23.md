# 冷启动 Skill 真实评估与 v4.2 复测（2026-08-23）

## 结论

三轮 MiMo + Tavily 真实运行先验证了“来源原子 → 任务 Barrier → 三路派生 → 双图编译”的主结构。随后 v4.2 把能力、知识技能和事理全部移出首屏关键路径：同一“内部开发者平台工程师”从 v4.1 的 138.1 秒降到 78.4 秒可用，下降约 43%；“DevOps 平台工程师”复测在 85.7 秒形成岗位—任务内核，之后自动提交知识/依赖子版本和事理/检查子版本。事实、来源和证据没有因低熵投影被删除。

## 固定测试方法

- 从产品的“新建岗位项目”入口启动；
- 使用相同会话级 Xiaomi MiMo 与 Tavily 配置；
- 开启自主联网研究；
- 每轮提供一个不同岗位和一段不同的真实工作观察；
- 以最终岗位包、工作项轨迹、快速快照时间、证据覆盖和节点语义共同评价；
- 不为任何岗位增加专用 prompt、关键词白名单或专用阈值。

### 第一轮：后端开发工程师

- 项目：`36f6f13c-592d-47fa-9ce5-ff5dee24e6d1`
- 结果：14 个任务、19 个知识技能、3 个能力、13 个事理场景；流程覆盖 85.7%。
- 主要失败：长来源分片反复生成截断 JSON，20 个工作项未恢复；未来信号和宽泛团队观点进入任务层，例如“训练机器与应用新技术”“调整团队协作模式”。
- 推导：来源必须先做证据角色路由，未来、教学和技术上下文不能进入任务关键路径；输出对象上限必须反推 token 预算。

### 第二轮：站点可靠性工程师

- 项目：`ad53ac7e-4a15-4fdf-9ff5-f2626cecf586`
- 结果：10 个任务、10 个知识技能、4 个能力、10 个事理场景；流程覆盖 100%。
- 改进：快速快照较第一轮下降约 67%，估算输入下降约 62%。
- 主要失败：6 个单段来源在 JSON 尾部截断，因无法继续二分而丢失；真实工作观察没有被正确提升为观察模式；部分公开实践页面形成过于宽泛的任务。
- 推导：单段工作项需要紧凑重试；任务 Barrier 必须读取来源资格与优先级；认识状态应由编译器依据证据来源确定，而不是照抄模型枚举。

### 第三轮：大模型算法工程师

- 项目：`74699b76-6cc0-446a-a294-ba7aaf204ebf`
- 快速快照：`snapshot:0df7cfe@2026-08-23:10fhqy7`
- 完整快照：`snapshot:0df7cfe@2026-08-23:04f1ugt`
- 结果：20 个来源、35 条 mention、21 条关系命题、10 个任务、11 个知识技能、3 个能力、9 个事理场景；0 个模型工作项失败。
- 质量：四个用户工作观察任务形成了清晰骨架；招聘来源补充了量化、硬件优化、基座研发与业务落地等岗位变体。job family 和产业链节点不再被方法或能力污染。
- 残余问题：任务 Barrier 后的知识、能力、事理在代码中仍按顺序等待；同一任务从不同组展开时产生同名事理场景；工作区片段只要被模型列为 evidenceSegment 就可能把无关场景提升为观察模式。

## 三轮后的 v3.3 修复

1. 任务 Barrier 后用一个 `Promise.all` 同时启动知识技能、跨任务能力和事理森林；每个 Lane 仍有独立并发上限与局部恢复。
2. 单段原子抽取失败时以 5 条 mention / 3 条 proposition 的紧凑协议重试；多段仍按局部二分恢复。
3. 普通原子抽取最多 6—8 条 mention / 4—6 条 proposition，输出上限按 2,000 / 2,600 token 分档；紧凑恢复上限 2,200。
4. 任务 Barrier 接收来源类型、证据角色、资格和通用优先级；工作区观察、标准与真实实践优先，低价值来源只能补独立交付边界。
5. 知识定点补研的新技术资料直接进入知识 Lane，不重复参与任务提取。
6. 事理场景和节点要把真实观察绑定为连续 `evidenceSpan`；编译器只用直接绑定或带 Workspace Evidence 元数据的正式工作区来源提升认识状态。
7. 事理场景、事件、边、桥和绑定按稳定 ID 合并，消除并发组重复对象。

| 岗位 | workflow | TASK BARRIER | 首个岗位内核 | 说明 |
|---|---:|---:|---:|---|
| 内部开发者平台工程师 | 4.1 | 105.4s | 138.1s | 内核仍等待能力/知识的模型工作 |

v4.2 的第一个版本只承诺岗位、代表任务、上下文、完整 SourceAsset/Segment/Mention/Proposition 和事理胶囊。能力、细粒度知识技能、技能依赖、事理森林和结构检查进入后台并行 Lane；它们分别形成同一 Static Role Package 协议下的不可变子版本。

## v4.2 DevOps 平台工程师端到端复测

- 项目：`59209f9a-c5a9-4a02-86ea-880e810cb56b`；真实使用产品会话中的 MiMo V2.5 与 Tavily。
- 首任务骨架 85.645 秒，首内核 85.667 秒；内核后约 68 秒完成全部后台增量。
- 版本链：岗位内核 → 知识技能与依赖 → 事理森林与结构检查，共三个不可变版本；父版本和节点引用均保留。
- 完整事实层：29 个节点、53 条语义关系、8 个任务、11 个知识技能、9 个能力/能力单元、13 条技能依赖、6 棵事理树、18 个过程节点。
- 当次页面从 7 个首屏节点自动增长到 16 个可见节点，并显示“后台增量完成”；事理森林可读取 6 个场景及任务映射。
- 结构协议、图遍历、证据解析、别名消歧与 Agent 上下文探针全部通过；事理模式均诚实保持 `inferred_pattern`，没有把公开资料冒充真实工作日志。
- 非阻断检查仍发现两项任务缺少技能/场景，以及 Kubernetes/Jenkins 近义技能簇。后续通用修复把默认雷达技能入口收紧为最多 5 个，并以命名技术锚点聚类；近义细项仍作为可寻址 facet 保留，未修改当次已生成的不可变版本。
