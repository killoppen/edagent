# 黄金岗位开放式研究与协作手册

## 这本手册怎样使用

黄金岗位研究不是一条只能从第一步走到第七步的流水线。团队成员可以从不同材料、不同问题和不同兴趣进入研究，并在阅读、发现、展示和提出假设之间反复往返。

可以把整个过程理解为两个区域：

- 自由发现区：广泛阅读、记录发现、互相展示、形成问题。这四项活动可以并行，也可以重复很多轮。
- 共同建模区：当某一类发现积累到足够程度后，团队才一起讨论典型任务、推导能力与事理过程，并形成阶段性版本。

研究的基本节奏是：

```text
广泛阅读 ⇄ 捕捉发现 ⇄ 互相展示 ⇄ 形成问题与假设
                                ↓ 材料逐渐成熟
                    讨论任务边界与粒度
                                ↓
                    推导能力并展开工作过程
                                ↓
                    审查、沉淀方法、形成版本
                                ↺ 新问题重新进入阅读
```

不要求所有成员在同一时间做同一件事。有人可以继续寻找来源，有人可以复核证据，有人可以比较任务边界，也有人可以尝试把一个成熟任务讲成真实工作故事。

## 研究动作一：自由选择线索，广泛阅读

### 简介

成员可以从自己感兴趣或擅长的入口开始，不需要先领到一个非常狭窄的题目。可阅读国家标准、企业官网 JD、招聘平台、员工自述、技术博客、项目复盘、演讲、开源仓库、Issue、PR、行业报告和课程标准。

自由阅读不等于毫无记录。团队只需要维护一个简单的来源台账，知道大家读过什么、来源属于哪一类、可能涉及什么问题，避免所有人只读同一种材料。

### 样例

```text
小林在牛客看到一篇大模型应用开发面经，注意到不同公司要求差异很大。

小周在企业官网看到“应用研发工程师”需要负责 API、Skill 和效果评估。

小陈在 GitHub Issue 中发现，工具调用失败后需要重试、降级和状态恢复。

三个人不必提前研究同一个问题，但这些材料后来可能共同支持
“Agent 应用构建与可靠性验证”的任务讨论。
```

### 注意

- 鼓励顺着材料中的人物、项目、术语和引用继续探索。
- 不规定每个人必须从 JD 开始，也不规定必须按来源等级依次阅读。
- 搜索摘要、转载标题和模型回答只能帮助发现线索，不能代替原文。
- 每隔一段时间检查来源结构，避免全部材料都来自招聘网站或培训内容。
- 匿名论坛适合发现问题，但不能单独证明岗位共性。

## 研究动作二：捕捉值得讨论的发现

### 简介

阅读后不要求每篇材料都填写完整表格。只有当某段内容带来新认识、产生冲突、暴露真实工作过程或可能影响岗位边界时，才制作一张简短的发现卡。

发现卡不是最终结论。它的作用是把个人脑中的“这个很重要”变成团队能够看到、核查和继续追踪的研究对象。

### 样例

```text
发现：应用工程师可能不仅负责开发，还要负责上线后的效果闭环。

我看到了什么：
某企业官方 JD 要求跟踪成功率、延迟和成本；一篇工程实践文章还描述了
从线上错误样本回到评测集的过程。

我的理解：
应用侧监测与迭代可能是岗位稳定任务的一部分。

我还不确定：
生产基础设施由应用工程师负责，还是由 LLMOps 团队负责。

建议：
先作为研究问题，不立即增加任务节点。
```

### 注意

- 先写“材料说了什么”，再写“我怎样理解”。
- 记录 URL、文件、页码、章节、段落或 Issue 编号，确保别人能回到原文。
- 一张发现卡可以只提出问题，不必同时给出答案。
- 不要因为发现暂时不能进入图谱就认为它没有价值。
- 同一材料可以产生多个发现，但不要把文章目录机械拆成大量卡片。

## 研究动作三：展示发现，交换岗位理解

### 简介

团队定期举行轻量的 Discovery Show & Tell。每个人展示近期最想让其他人知道的一项发现，重点讲“这条材料如何改变了我的理解”，而不是汇报自己阅读了多少页面。

展示是开放交流，不是答辩。其他成员可以补充相似材料、提出反例、指出岗位混称，也可以说出自己从该发现联想到的新问题。

### 样例

```text
展示者：
我原来认为“模型微调”是大模型应用工程师的核心任务。

新材料：
我阅读的多个应用岗位只把微调列为加分项，但算法岗位把训练和对齐写成主要职责。

我的新判断：
微调可能是条件性职责，不应直接作为所有应用工程师的核心任务。

组员补充：
小型企业可能由同一个人同时承担应用和微调，需要继续研究企业规模差异。

会议结果：
保留“微调是否属于稳定内核”为争议问题，继续收集反例。
```

### 注意

- 每人一次重点展示一项发现，建议控制在五分钟左右。
- 尽量直接打开原文和发现卡，不只展示重新制作的 PPT。
- 展示后可以产生新的线索、问题或候选，但不自动形成正式结论。
- 不要求每次展示都与当前任务骨架一致，意外发现往往最有价值。
- 讨论重点是证据、适用范围和解释，不是判断发言者对错。

## 研究动作四：建立问题与假设池

### 简介

当不同发现开始相互关联时，团队把它们整理成研究问题或暂时假设。问题池允许团队保留尚未成熟的方向，不必急着把所有认识变成图谱节点。

假设可以指导后续搜索，也可以被反例推翻。它应当带有当前依据、适用范围和升级条件。

### 样例

```text
研究问题：
大模型应用工程师是否稳定承担应用发布和运行监测？

当前假设：
应用效果、业务指标和错误样本闭环属于岗位内核；
模型服务集群、GPU 调度和组织级平台运维通常属于 LLMOps/AI Infra。

支持材料：
三份企业官方 JD、两篇实名工程实践。

反例：
一家小型企业要求应用工程师同时维护推理服务。

下一步：
补充小型企业与大型企业样本，并查找真实交接或事故材料。
```

### 注意

- 假设不是事实，也不是正式节点。
- 允许同时保留两个竞争性解释，不必马上投票。
- 写清楚什么新证据会支持、削弱或推翻假设。
- 区分岗位稳定内核、常见变体和特定企业组合职责。
- 问题长期无法解决时，可以保留为 `disputed` 或研究缺口。

## 研究动作五：材料成熟时，共同讨论任务边界

### 简介

只有当一批发现已经能够说明真实工作对象、行动和交付结果时，才进入任务建模。团队把相关发现放在一起，比较哪些属于同一任务、哪些应当分开、哪些只是工具或步骤。

任务骨架是阶段性稳定的，不是永久不可修改。新的行业材料或真实工作记录出现后，可以重新打开讨论。

### 样例

```text
原始发现：
文档解析、分块、向量化、召回优化、重排序、回答引用、错误样本分析。

讨论：
这些活动是否分别成为典型任务？

比较结果：
它们围绕同一知识对象，共同形成一条知识增强链路，
最终由同一组效果和集成要求验收。

阶段性任务：
构建并验收面向业务场景的知识增强应用。

任务内部步骤：
知识准备、检索构建、生成约束、评测优化和集成交付。
```

### 注意

- 用四个问题检查任务：处理什么对象、采取什么行动、交付什么、何时算完成。
- “RAG”“Agent”“LangChain”“性能分析”不是合格任务名称。
- 差异只是工具、参数或实现策略时，通常不应拆成多个任务。
- 能独立受理、独立交付并独立验收的工作，可以考虑拆分。
- 不为了达到任务数量而制造节点，也不为了图谱简洁过度合并。

## 研究动作六：围绕任务展开能力和真实工作故事

### 简介

任务骨架相对稳定后，可以并行开展两类研究：一类寻找多个任务共同需要的可迁移能力，另一类把代表性任务展开为具体工作场景。知识和技能则放回任务与工作事件中理解。

这里仍然允许自由探索。有人可以研究能力表现，有人可以寻找失败和返工案例，也有人可以尝试面向学生讲解任务。

### 样例

```text
典型任务：
构建知识增强应用、构建 Agent 应用、开展应用评测、推进业务集成。

跨任务能力：
大模型应用方案设计与技术取舍。

可观察的能力单元：
给定业务目标、数据条件和风险约束，能够比较直接调用、RAG、
工作流和 Agent 等方案，形成有依据的技术方案。

代表性工作故事：
业务提出客服自动答疑需求
→ 检查知识资料
→ 建立最小应用
→ 构建测试集
→ 分析错误并返工
→ 接入业务系统
→ 灰度验证
→ 上线监测与持续改进。
```

### 注意

- 岗位能力应当跨多个任务成立，不能只是框架或技术名称。
- 能力单元必须能够通过行为、过程或交付结果观察和测评。
- 知识点回答“需要理解什么”，技能点回答“能够完成什么操作”。
- 事理场景要包含触发、参与者、产物、判断、异常、返工和验收。
- 不要求每项任务拥有相同规模的能力映射或事理树。
- 没有真实企业记录时，要明确它是规范描述或研究归纳，而不是流程实录。

## 研究动作七：阶段性收束，并把经验留给下一轮

### 简介

团队不必等到“所有问题都解决”才形成版本。当核心任务、主要关系和代表性场景达到当前可接受质量时，可以阶段性冻结，同时保留候选、争议和研究缺口。

收束时不仅记录岗位结论，还要记录优秀研究方法、失败做法、粒度判断经验和适合教学展示的讲解顺序。这些内容以后可以转化为 AI 生成规则和评测案例。

### 样例

```text
本轮内容决定：
“调整分块策略”和“优化召回排序”保留为知识增强任务中的技能行为，
不拆成两个典型工作任务。

本轮形成的方法：
判断一个候选是否为任务时，优先比较工作对象、最终交付物和验收责任，
不能只看它在技术文章中是否有独立标题。

本轮形成的评测案例：
“调整文档分块大小”应判为技能行为；
“构建并验收知识增强应用”可以判为典型工作任务。

下一轮问题：
不同行业对知识安全、人工复核和上线审批的责任边界是否不同？
```

### 注意

- 只有接受内容进入正式黄金岗位包，研究过程和讨论记录单独保存。
- 记录新增、合并、拆分、改名、暂缓及其理由。
- 保留反对证据和少数意见，避免只留下胜出的结论。
- 一次岗位研究中有效的方法，不自动升级为所有岗位的普遍规则。
- 冻结版本不是研究结束，新证据可以进入下一版本。

## 根据目的选择协作活动

### 开放发现会

适合研究初期或需要打开新方向时使用。成员自由分享近期发现、材料线索和困惑，不要求当场形成任务或能力结论。

建议时长：45—60 分钟。

### 证据核查会

适合某个重要结论准备进入图谱前使用。团队共同查看原文、来源资格、适用范围、支持关系和反例。

建议时长：45—60 分钟。

### 任务边界工作坊

适合相关发现已经形成一定聚类时使用。集中比较候选任务的对象、行动、交付物和完成边界。

建议时长：60—90 分钟。

### 工作故事走查会

适合任务骨架形成后使用。由一名成员讲述任务如何在真实场景中发生，其他成员补充分支、异常、协作和验收。

建议时长：60 分钟。

### 阶段审阅会

适合准备形成候选版本或冻结版本时使用。检查证据、语义图、事理森林、争议和展示逻辑是否一致。

建议时长：60—90 分钟。

## 可以形成哪些有价值的产出物

下面是一份灵感清单，不是每轮研究都必须完成的作业表。团队应根据当前问题选择最有帮助的产出物；有些保持为工作草稿，有些经过审阅后才进入黄金岗位包。

### 来源地图

把已经阅读和仍然缺失的来源按类型、行业、企业规模、资历层级和时间分布画出来。它能提醒团队：我们是否过度依赖招聘 JD，是否缺少真实项目、事故复盘或员工工作叙述。

### 发现卡墙与研究问题池

发现卡墙保存成员带回来的新线索、冲突和反例；问题池保存尚未解决的岗位问题。它们让有价值但尚不成熟的信息继续流动，不必过早塞进正式图谱。

### 岗位别名与边界图

列出“大模型应用工程师”的常见别名，并与算法工程师、AI Agent 工程师、后端工程师和 LLMOps 工程师比较核心对象、主要交付物、常见协作和容易混入的职责。它适合解释岗位身份，也能暴露企业混称。

### 任务候选簇

把材料中的职责、动作、产物和事件写成卡片，再按共同工作对象和交付结果聚类。任务候选簇不是最终图谱，而是形成 TASK BARRIER 前可移动、可合并、可拆分的工作台。

### 典型任务剖面卡

每个成熟任务用一页说明触发、对象、行动、产物、验收、协作、异常和适用范围。它既能帮助团队判断任务粒度，也能直接成为面向学生和教师的讲解单元。

### 任务—能力—证据矩阵

用矩阵检查哪些能力真正跨越多个任务、哪些能力单元有可观察表现，以及每条重要关系由什么证据支持。矩阵主要用于发现孤立节点、单任务“能力”和证据空洞，不必成为最终前端页面。

### 关键工作故事与事理场景图

选择最能体现岗位价值、风险和协作的任务，讲清工作怎样从触发走到交付，并包含判断、异常、返工和回滚。相比理想化流程图，带有失败与交接的工作故事更接近真实岗位。

### 冲突、反例与研究决定台账

记录哪些材料互相矛盾、哪些结论只适用于某类企业，以及团队为什么合并、拆分、改名或暂缓一个候选。它能防止最终版本看似整齐，却丢失了判断依据。

### 规则卡与冻结评测案例

把研究中反复有效的判断写成“规则、适用范围、正例、反例、例外”，并冻结一批分类、合并、证据和问答案例。规则不是口号；评测案例才说明后续 AI 是否真正学会了粒度和证据纪律。

### 多角色讲解脚本

分别尝试向学生、教师和企业人员解释同一个岗位。学生关心“我将做什么、怎样学习”，教师关心“如何转成学习任务与评价”，企业人员关心“是否符合真实分工”。三种讲法可以启发后续信息架构和前端展示。

## 可以尝试哪些研究方法

方法也不是固定工序。遇到不同问题时选用不同方法，并记录它在什么条件下有效、产生了什么偏差。

### 滚雪球阅读

从一份高质量材料出发，继续追踪其中的术语、作者、引用、项目、仓库和相关人物。它适合打开陌生领域，但要定期回看来源地图，避免被单一圈层带偏。

### 最大差异取样

有意识地选择大型与小型企业、ToB 与 ToC、不同产业、初中高级岗位和不同年份的材料。它不追求样本数量最多，而是帮助团队区分稳定岗位内核与情境性组合职责。

### 对照阅读

把同名岗位在不同企业的描述放在一起，或把相邻岗位围绕同一工作对象进行比较。不要只统计关键词，要比较谁负责决策、谁交付、谁验收、谁承担失败后的处理责任。

### 产物反推法

先寻找真实交付物，例如技术方案、评测报告、接口服务、知识库、监测看板或上线复盘，再反推为了完成它发生了哪些工作。这个方法有助于避免把工具名和技术步骤误判为典型任务。

### 关键事件法

重点寻找上线失败、效果退化、数据问题、成本超限、越权调用、事故处理、返工和交接事件。关键事件往往比顺利完成的宣传案例更能暴露判断条件、协作边界和真实能力。

### 卡片聚类与边界比较

先允许成员用自己的语言写任务候选，再根据工作对象、最终产物、验收责任和完成边界进行聚类。聚类后必须专门比较“为什么合并”和“为什么不能合并”，不能只凭名称相似度。

### 多来源三角互证

让不同性质的材料回答同一个问题：标准说明应当做什么，企业材料说明谁被要求做，真实项目材料说明实际上怎样做。三类材料互相补足，但不能把数量简单换算成可信度。

### 主动寻找反例

当团队形成一个顺手的解释后，指定成员去寻找能推翻它的岗位、企业或事件。反例不是给结论“找麻烦”，而是帮助写清适用范围、例外和重新打开讨论的条件。

### 场景走查

让成员分别扮演业务方、应用工程师、算法工程师、平台工程师和验收方，从需求触发一路走到上线与迭代。凡是讲不清输入、交接、判断、失败和验收的位置，都是需要继续研究的缺口。

### 讲给别人听

请一名成员不看图谱，面向学生讲清一个任务，再由其他成员追问“为什么这样做、凭什么验收、失败怎么办”。如果只能罗列术语，通常说明研究还没有形成可理解的工作逻辑。

### 决定与重开条件

每次重要收束都同时记录当前决定和重新打开它的条件。例如，新行业样本出现、真实交接材料与当前边界冲突或现有任务无法独立验收时，应重新讨论。这样既能形成版本，也不会把阶段性共识误当成永恒真理。

## 最后的提醒

好的黄金岗位研究不是让所有人快速得到同一个答案，而是让不同成员能够自由发现、公开证据、比较解释，并在适当的时候形成可追溯的阶段性共识。

研究的自由度来自开放入口和允许反复探索；研究的质量来自证据纪律、清晰区分事实与推断，以及对每次重要决定的认真记录。
