# 新建岗位项目：产品与交互规格 v0.2

状态：`proposed`\
适用对象：Role Atlas 冷启动生成 Skill\
主要用户：计算机类高职学生、教师；兼容企业、其他专业与其他学段\
关联规范：`cold-start-orchestration.md`、`build-event-protocol.md`、`versioning-and-publication.md`、`cold-start-graph-algorithms.md`、`work-process-event-graph-research.md`

## 1. 产品结论

新建项目不是“填写长表单后等待报告”，也不是只能输入文字的聊天向导，而是一段**对话主导、结构化控件辅助、研究过程可见、图谱逐层涌现**的岗位研究过程。

用户只需要表达一个可能模糊的岗位或岗位方向，并可选接入一个工作区。Agent 负责：

1. 从模糊输入形成可修订的岗位目标假设；
2. 只在答案会显著改变研究对象时提出问题；
3. 并行研究公开资料与用户工作区；
4. 按语义依赖生成岗位边界、任务、能力、能力单元和知识技能；
5. 在生成期间持续聚类、去重、分类和绑定证据；
6. 自动把候选内容写入工作图谱；
7. 把一次有效构建保存为版本，按需标记 Tag；
8. 将可发布版本编译成 Static Role Package，而不是直接修改已发布快照。

图谱不是最终报告的装饰，而是 Agent 研究状态、岗位结构和证据覆盖的共同界面。

## 2. 核心体验原则

### 2.1 对话主导的混合交互

入口以自然语言承接模糊意图、解释判断和启发用户；在答案空间已经明确时，使用选项卡、短表单、资料选择器、预览确认和“跳过/按推荐继续”。不要求用户理解岗位分类、图谱 schema、来源类型或构建参数。

对话负责“为什么”和“还不确定什么”，控件负责“从已知选项中高效表达决定”。控件提交后必须回写为可读的会话记录，保证运行可恢复、可审计。

### 2.2 边界渐进收敛

岗位边界不是创建前必须填对的字段。系统维护 `RoleTargetHypothesis`，随着研究不断修订，并保留修订理由。

### 2.3 自动进入工作图谱

候选节点和关系生成后直接进入工作图谱。用户不需要逐个审批；候选、稳定、异常和已发布状态必须可区分。

### 2.4 有效工作可见

运行信息遵循“行动 → 原因 → 结果 → 图谱影响”，不向用户倾倒无意义日志。模型返回的思考过程可单独展开实时查看。

### 2.5 并行但不混乱

系统允许多个研究分支同时运行，但每个分支必须有名称、目标、输入、当前产物和归并点。主界面始终只突出当前最有价值的变化。

### 2.6 语义纪律持续执行

聚类、同维度去重和维度污染检查必须发生在生成过程中，不能等全部节点产生后再做一次补救式清洗。

### 2.7 版本是版本，Tag 是 Tag

工作图谱类似 Git working tree；一次构建结果类似 commit；Tag 是面向用户的重要里程碑名称；已发布岗位包是从某个版本编译的不可变制品。

## 3. 新建项目入口

点击左侧“新建岗位项目”后，主区域进入创建态，右侧对话框获得焦点。

首屏只显示：

```text
你想了解什么岗位或岗位方向？
[例如：大模型应用工程师；AI 相关岗位；我想做能开发智能体的工作……]

[选择工作区] [上传资料] [开始]
```

### 3.1 首屏字段

必需：

- 一段岗位或岗位方向描述。

可选：

- 选择已有工作区；
- 选择本地目录；
- 上传一组文件；
- 指定“不联网，仅分析资料”；
- 补充用途或关注点。

当前不要求：

- 用户手工选择实体类型；
- 用户填写完整地区、行业和资历表单；
- 用户估计任务、能力或知识技能数量；
- 用户选择图谱布局或底层模型参数。

### 3.2 工作区选择

工作区可以是：

- 真实项目代码、文档和交付物；
- JD、岗位描述或招聘资料集合；
- 专业标准、人才培养方案、课程资料；
- 企业流程、规范和内部知识资料；
- 多类材料混合目录。

选择后先展示扫描预览：文件数量、类型概况、预计可识别内容和需要排除的敏感项。工作区内容默认归类为私域来源，不能在界面或 Agent 回答中被误称为公开市场共识。

## 4. 对话式澄清协议

### 4.1 岗位目标假设

Agent 的第一个结构化产物是 `RoleTargetHypothesis`：

```yaml
working_title: 大模型应用工程师
target_kind: market_role
aliases: [LLM 应用工程师, AI 应用工程师]
scope:
  country: CN
  markets: [中国公开招聘市场]
  industries: []
  seniority: [初级, 中级]
  audience: [student, teacher]
inclusions: []
exclusions: []
adjacent_candidates: []
unknowns: []
confidence: 0.58
revision: 1
```

这是项目工作状态，不是岗位事实，也不直接进入发布包。

### 4.2 提问判定

只有满足至少一项时才中断询问：

1. 两个解释会产生明显不同的核心任务集合；
2. 用户输入可能指岗位群，而当前项目必须确定一个核心市场岗位；
3. 是否使用私域资料、是否联网或地域范围无法安全推断；
4. 缺少的信息会导致昂贵研究分支大概率无效；
5. 用户给出的资料存在无法自行处理的授权或隐私问题。

不应中断询问：

- 可使用合理默认值并显式记录的字段；
- 可以通过公开研究解决的别名或分类问题；
- 只影响展示而不影响语义的偏好；
- “是否还要补充”式无目的问题。

### 4.3 问题呈现

每轮最多提出三个相互关联的问题，并说明影响：

> 你提到“AI 工程师”。目前有两个任务边界明显不同的解释：偏模型训练，或偏业务应用交付。这个选择会改变后续任务和知识技能图谱。你更关注哪一个？

如果答案可以穷举，问题下方直接渲染选项，并同时允许自由回答、跳过或选择“先按 Agent 推荐继续”。如果需要用户描述经历、目标或资料含义，才使用开放文本。

### 4.4 交互形式选择

| 信息任务 | 默认交互 | 原因 |
|---|---|---|
| 表达模糊岗位意图、疑惑、个人目标 | 自然语言 | 需要保留用户自己的表述与潜在线索 |
| 在两个或三个岗位边界间取舍 | 选项卡 + 影响说明 + 自由回答 | 答案空间清楚，选择会改变研究分支 |
| 地区、受众、联网、资料范围 | 紧凑字段/多选 | 信息原子化且适合快速修改 |
| 选择工作区、上传资料、排除目录 | 专用选择器 + 扫描预览 | 需要权限、范围和敏感信息反馈 |
| 接受可解释默认值 | “按推荐继续” | 避免为低风险未知量阻塞运行 |
| 非关键问题 | “跳过” | 将默认值及其风险写入 Brief，不制造无目的追问 |
| 研究计划、边界假设、发布前摘要 | 可展开审阅卡 | 用户需要看到结构，又不应被迫填写完整表单 |

不得把一个长表单拆成十轮伪对话；也不得为了维持“聊天感”而让用户用文字输入本可一次点击完成的确定选择。

### 4.5 无需确认即可开始的条件

满足以下条件后自动启动研究：

- 能形成一个核心岗位假设；
- 可以声明默认地区、市场和快照时间；
- 没有待解决的资料授权问题；
- 至少有一种可用来源策略。

## 5. 运行中的页面模式

创建完成后仍使用三栏工作台，但进入 `build mode`。

### 5.0 页面状态流

```text
创建态                 澄清态                 构建态
┌────┬────────┬────┐   ┌────┬────────┬────┐   ┌────┬────────┬────┐
│项目│ 岗位空态│对话│   │项目│边界假设│问答│   │项目│生长图谱│进程│
│列表│ 工作区  │输入│ → │列表│与资料预览│卡片│ → │运行│与层级  │对话│
└────┴────────┴────┘   └────┴────────┴────┘   └────┴────────┴────┘
                                                   ↓
                                             收敛/审计/版本态
                                             ┌────┬────────┬────┐
                                             │历史│稳定图谱│总结│
                                             │版本│与风险  │对话│
                                             └────┴────────┴────┘
```

三栏的几何结构保持稳定，用户不会因为阶段变化重新学习页面；改变的是中间主任务和右侧信息层级。

### 5.1 左侧：项目与运行

显示：

- 项目名称和工作状态；
- 当前构建运行；
- 自动版本和 Tag；
- 项目会话；
- 暂停、继续、取消入口；
- 工作区和资料范围。

项目应在用户点击开始后立即出现，不能等生成完成后才加入列表。

### 5.2 中间：生长中的图谱

顶部保留岗位标题，但增加边界状态：

```text
大模型应用工程师
边界假设 r3 · 正在验证 · 24 个来源
```

图谱工具条增加：

- `生长视图`：当前默认；
- `岗位雷达`；
- `卡片总览`；
- `任务—能力`；
- `学习路径`；
- `证据视图`；
- `运行回放`。

生长视图显示：

- 当前正在形成的语义层；
- 已稳定层；
- 活跃分支；
- 最近新增、合并或移除的节点；
- 每个节点的来源、置信和生命周期摘要。

### 5.3 右侧：Agent 对话与运行叙事

右侧同时容纳三种内容：

1. Agent 和用户的自然语言对话；
2. 结构化运行活动；
3. 可展开的模型思考过程和工具细节。

当 Agent 等待用户决定时，可在消息流中嵌入选项卡、短表单、文件范围预览和审阅卡。它们是会话消息的一部分，不打开遮挡图谱的独立向导；提交后锁定为历史记录，并允许用户通过新消息修订。

默认运行卡只显示：

```text
正在并行分析 18 份 JD、2 份职业标准和工作区中的 43 个文件
已提取 37 个任务表达，归并为 9 个候选任务簇
图谱新增 7 个任务节点、14 条关系；合并 6 个重复表达
```

展开后才显示：

- Plan；
- 并行 Lane；
- 工具名称和参数摘要；
- 重试和错误恢复；
- 模型 reasoning；
- 候选对象和证据绑定详情。

### 5.4 并行 Lane

默认 Lane：

- 岗位边界；
- 职业标准；
- 招聘市场；
- 公开实践资料；
- 用户工作区；
- 任务聚类；
- 能力归纳；
- 知识技能；
- 证据绑定；
- 语义审计。

Lane 可以折叠，主界面最多同时突出三个活跃 Lane。其余只显示状态和数字，避免争夺注意力。

## 6. 图谱生长语义

### 6.1 视觉状态

| 状态 | 含义 | 建议表现 |
|---|---|---|
| `emerging` | 刚产生，内容仍在补全 | 半透明、虚线、轻微呼吸 |
| `candidate` | 结构完整，待全局归并或审计 | 虚线、候选徽标 |
| `stable` | 本次工作图谱内已稳定 | 实线、正常透明度 |
| `attention` | 证据、边界或语义有重要问题 | 黄色标记并说明问题 |
| `rejected` | 已被归并、越界或拒绝 | 从默认图谱收起，可在历史中查看 |
| `published` | 来自已发布岗位包 | 实线并带版本标识 |

不能仅依靠颜色区分状态；边框、透明度、徽标和文本要共同表达。

### 6.2 图谱补丁节奏

图谱不跟随每个 token 抖动。只有形成完整语义动作时才更新：

- 新建候选节点；
- 补全节点摘要；
- 新建关系；
- 合并节点；
- 修订岗位边界；
- 改变生命周期；
- 绑定新证据；
- 发现审计问题。

同一批语义动作以一个原子 `graph.patch` 呈现。动画只解释变化，不得延迟真实结果。

### 6.3 语义层顺序

1. 岗位种子；
2. 职业标准、产业链、岗位群、相邻岗位；
3. 典型工作任务；
4. 跨场景能力；
5. 能力单元；
6. 知识技能。

来源、证据、风险和研究主题作为叠加视图，不新增到岗位雷达的默认环层，避免维度混乱。

允许多个分支并行生长，但能力必须在足够的任务候选形成后进行跨任务归纳；不能让每个任务分支各自发明一套能力。

## 7. 注意力契约

用户应始终能在一个视口内回答四个问题：

1. Agent 现在在做什么？
2. 为什么这一步有价值？
3. 最近产生了什么可见结果？
4. 是否需要我做什么？

界面不得出现：

- 长时间只有旋转图标；
- 大量重复“正在分析”；
- 工具调用刷屏但没有产物；
- 所有并行分支同等突出；
- 通过虚假动画掩盖没有真实进展；
- 因对话变长把图谱推出视口。

建议首期性能目标，不作为外部承诺：

- 项目壳创建：1 秒内；
- 初步岗位假设：10 秒内；
- 第一条真实来源活动：20 秒内；
- 中心岗位与第一层候选：60 秒内；
- 首批任务簇：3 分钟内；
- 任意 15 秒窗口内，存在有效进度、可见产物或明确等待原因之一。

## 8. 用户反馈与后续修改

首期不把复杂图谱编辑器作为主要入口。用户对节点有疑惑或不满意时，通过以下方式进入对话：

- 点击或拖拽节点；
- 引用一组节点；
- 引用一次审计问题；
- 直接描述不满意之处。

Agent 应把自然语言意见转为 `change proposal`，说明将修改哪些节点、关系、证据或边界。是否自动应用由统一“岗位快照迭代”Skill 定义，不与冷启动主流程耦合。

## 9. 成功标准

一次第一版冷启动完成，应满足：

- 形成单一核心市场岗位及清晰边界；
- 岗位雷达主要维度齐全；
- 同维度不存在明显语义重复节点；
- 任务有独立交付物和验收含义；
- 能力来自跨任务表现归纳；
- 知识技能可以学习、实践或测评；
- 不存在默认视图中的孤立核心节点；
- 重要节点与关系有可追溯来源；
- 节点简介完整、概括性强、重点突出；
- 构建过程可回放、可恢复、可解释；
- 用户可以用较低理解成本开始有价值的岗位对话。

## 10. 明确不做

首期不做：

- 在创建前要求用户配置完整 ontology；
- 为每个候选节点安排人工审批；
- 把所有模型 token 映射为图谱动画；
- 把工作区观察直接当作公开岗位共性；
- 在已发布静态岗位包上原地写入生成结果；
- 同时生成多个核心市场岗位的完整快照。

用户输入岗位大类时，首期通过对话收敛为一个核心岗位，其他岗位作为岗位群或相邻岗位出现。多核心岗位对比是独立的后续能力。
